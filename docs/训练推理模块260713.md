## 二、导致类别不一致的其他可能原因

除了上面这个“标签没加载”问题，还需要从四个维度系统排查：

| 环节 | 常见问题 | 影响 |
|---|---|---|
| **类别映射** | `labels.json` 顺序与模型输出索引不一致；manifest 未记录；标签文件缺失 | 类别名整体错位或显示 `Class_<id>` |
| **预处理** | `inputSize`、归一化 `mean/scale`、通道顺序 `swapRB`、resize 与 letterbox 不一致 | 输出概率分布改变，极端时.argmax 索引变化 |
| **后处理** | 分类分支重复 softmax（模型已带 softmax 时）、YOLO v5/v8 格式判断错误、置信度阈值过高/过低 | 置信度异常或漏检，类别索引解析错 |
| **模型导出** | 导出 ONNX 时 `class_to_idx` 与训练不一致；背景类处理不同；动态轴未固定 | 即使标签正确，索引本身也错 |

#### 2. 进程异常退出 `code -1073741819`（0xC0000005）
- **根因**：CPU 版 PyTorch + Windows DataLoader + OpenCV 组合下，CPU 内存/线程压力更大，易触发访问冲突。代码虽已做 `cv2.setNumThreads(0)` / `cv2.ocl.setUseOpenCL(False)` 和 `num_workers=0` 等防护，但无法弥补 **CUDA 不可用 + 架构不兼容** 的根本问题。

```cpp
void InferencePanel::setProgress(int value, int total, const QString& status) {
    m_progressBar->setVisible(true);

    if (total <= 0) {
        m_progressBar->setRange(0, 0);
        if (!status.isEmpty()) m_statusLabel->setText(status);
        return;
    }

    m_progressBar->setRange(0, total);
    m_progressBar->setValue(qBound(0, value, total));

    int percent = total > 0 ? static_cast<int>(value * 100.0 / total) : 0;
    QString text = QString("已完成 %1% (%2/%3)").arg(percent).arg(value).arg(total);
    if (!status.isEmpty()) text = status + " " + text;
    m_statusLabel->setText(text);
}
```

### 3.3 问题 c：验证准确率异常波动

**现象**：Epoch 3/20 的 Val Acc 突降至 47.5%，其他 Epoch 为 100%。

**根因分析**：
1. **数据划分随机性**：原先按类别随机划分训练/验证集，小样本类别容易出现验证集样本数极少（甚至 1 张），单张预测错误会直接将准确率拉低。
2. **样本不平衡/过少**：某些类别仅有 1~2 张样本。
3. **缺少确定性种子**：不同训练 run 划分结果不同，指标不可复现。

**修复方案**：

- **C++ 数据划分优化**（[`src/AI/TrainingBridge.cpp`](file:///e:/anchor/Trae/QDV/src/AI/TrainingBridge.cpp#L75-L109)）：
  - 每类至少保留 1 个训练样本；
  - 样本数 ≥ 2 的类别至少保留 1 个验证样本；
  - 使用 `qHash(类别名) ^ qHash(样本数)` 生成确定性种子，保证可复现；
  - 样本过少时输出警告日志。

- **Python 端随机种子**（[`training/train.py`](file:///e:/anchor/Trae/QDV/training/train.py#L252-L253)）：
  - 在构建 DataLoader 前调用 `_set_random_seeds(42)`，同步 Python/NumPy/PyTorch/CUDA 随机性。

- **验证集为空兜底**（[`training/engine/trainer.py`](file:///e:/anchor/Trae/QDV/training/engine/trainer.py#L264-L270)）：
  - 当 `len(val_loader) == 0` 时，使用训练指标作为验证指标并提示用户增加样本。

**预期效果**：消除因“验证集只有 1 张样本且预测错误”导致的 47.5% 准确率断崖；指标稳定且可复现。

## 三、根因分析

### 3.1 直接原因
`TrainingInferenceView::rebuildImageList()` 在加载 507 张图像时，**一次性同步创建 507 个复杂自定义 widget**（每个包含 `QCheckBox` + `QWidget` 缩略图容器 + `QLabel` 文件名 + `QLabel` 类别标签 + 布局 + 样式表）。

这会导致：
1. **内存峰值骤增**：每个 widget 及其子控件、缩略图 QPixmap 同时驻留，接近或触发内存碎片/访问异常。
2. **事件队列积压**：大量 widget 创建产生大量 pending 事件；后续代码中虽已调用 `processEvents`，但触发时机在全部 widget 创建完毕之后，中间阶段事件队列过长。
3. **延迟删除对象与新建对象交错**：`QProgressDialog` 刚被 `deleteLater()`，紧接创建大量 widget，事件循环处理延迟删除时可能与新 widget 的 Qt 内部资源冲突，触发 `ACCESS_VIOLATION`。

### 3.2 加载流程时序
```
onLoadProject() → loadAsync() → 工作线程 IO/JSON 解析
                              ↓
onLoadFinished() → 关闭进度对话框(deleteLater)
                 → fromJson() / restoreDataFromProject()
                 → rebuildImageList()  ← 崩溃高发点
                 → 缺失图像对话框
```

### 3.3 排除的其他因素
- **线程安全**：`ProjectSerializer::loadAsync()` 已限制工作线程只做文件 I/O 与 JSON 解析，不访问 `TrainingProject` / Manager，符合安全设计。
- **fromJson 数据过滤**：新添加的 `reset()` 仅发射 `modifiedChanged(false)`，无悬空指针问题。
- **CategoryPanel 数量显示**：仅遍历图像做统计，时间复杂度 O(C×N)，类别数通常很少，不会导致崩溃。

## 二、根因重新定位

`QListWidget::clear()` / `QTreeWidget::clear()` 并不会**立即**删除子 widget，而是将删除事件投递到 Qt 的 `DeferredDelete` 队列。当 507 个自定义 widget 被清除后：

1. 旧 widget 进入延迟删除队列；
2. 代码立即创建 507 个新 widget；
3. 新 widget 与尚未销毁的旧 widget 共享同一 `QListWidget` 视口；
4. `setCurrentRow` / 窗口重绘 / `QProgressDialog` 关闭 触发事件循环；
5. Qt 在处理延迟删除时访问到已被覆盖或半销毁的内部节点，触发 `ACCESS_VIOLATION`。

此前仅增加“循环中 processEvents”无法解决，因为：
- 旧 widget 仍挂在 item 上，`clear()` 才会投递删除；
- 退出函数后的事件脉冲才是真正触发崩溃的时刻。

## 一、根因分析

### 1.1 加载 vs 保存差异

| 操作 | 数据量 | 关键路径 |
|---|---|---|
| 加载（已稳定） | 500+ 张图 | 解析 JSON → 重建 `QListWidgetItem` 原生列表 |
| 保存（仍闪退） | 50+ 张图 | 收集快照 → 若为打包模式则**读取所有图像文件 → 压缩 → 写入** |

### 1.2 打包保存的内存风险
原 `ProjectSerializer::saveBundledModeWithData()` 存在以下问题：

1. **每个图像被完整读入内存两次**  
   - 第一次：`srcFile.readAll()` 计算 SHA-256 并写入临时目录
   - 第二次：打包时再次 `f.readAll()` 写入 `archiveData`
2. **`archiveData` 无预分配**  
   反复 `append` 导致 QByteArray 多次重新分配/拷贝，堆压力剧增。
3. **`qCompress(archiveData, 9)` 再复制一份压缩数据**  
   内存峰值 ≈ 2 倍原始数据大小。
4. **无大小限制**  
   50 张高分辨率工业图像（例如每张 20~50MB）即可轻松撑爆可用内存，触发系统终止或堆损坏闪退。
5. **保存完成后立即 `QMessageBox`**  
   `QProgressDialog` 的 `deleteLater` 与模态对话框的嵌套事件循环冲突，可能放大崩溃概率。

```cpp
while (!srcFile.atEnd()) {

    if (read > 0) hash.addData(buffer.data(), static_cast<int>(read));
}
```

```cpp
if (!QFile::exists(newPath)) {
```

```cpp
constexpr qint64 kReserveCap = 100LL * 1024 * 1024; // 100 MB
```
