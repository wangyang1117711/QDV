## 一、评估结论摘要（先结论）

1. **09:40 v1.0 版报告的两个 Critical 判定已过时，本次修正**：
   - ~~幻影算子 Reconstruct3D/BinocularDisparity/SurfaceMatching 拖入即崩~~ → **已修复**：`config/operators.json`（08-14）与 `build/bin/config/operators.json`（09-06 部署）均为 70 个算子，与 `ToolFactory.cpp` 70 条注册**程序化比对完全一致**，三个幻影算子已全部移除；
   - ~~ToolChainExecutor::execute() 恒返回 true~~ → **已修复**（P1-A2）：现统计 `failCount`，任一工具失败且非分支容错时链返回 `false`，并新增 `toolFailed` 信号透传具体错误信息（`src/Vision/ToolChainExecutor.cpp:391-421`）。
2. **当前真实最大差距（对标 SCMVS 视频实证）**：**产线对接通路缺失**——SCMVS 具备数字 IO（LINE0-3 + 输出条件/持续/延迟/有效电平）+ **Modbus TCP（Server/Client、字节序、控制/状态/结果/指令四区寄存器）** + FTP 三通路；QDV 仅有 TCP 完整、串口存根（P1-C8 已加警告）、IO 模拟，**无 Modbus、无 FTP**，无法与 PLC/MES 完成产线闭环。
3. **产品形态是"定位差异"而非"差距"**：SCMVS 是"PC 配置端 + 智能相机端离线执行"的边缘形态；QDV 是 PC 端一体化平台（编辑+执行+训练+零样本）。QDV 在**算子广度（70 个/18 分类）、训练闭环（QDVAnnotator 标训回灌）、零样本能力（ZeroShotKit）**上反超 SCMVS，但在**引导式工作流、方案级基准图、产线通信、采集即用交互**四处落后。
4. **交互性差距的本质是"孤岛"而非"缺失"（v2.1）**：CameraView v5.3.3 已有实时预览与实时调参、setCameraFrame 预留接口已存在，但能力锁在单视图内——采图即基准图、采图即训练样本、编辑全程可见画面三条 SCMVS 便捷路径均因"相机→编辑器/训练视图"管道未通而不可用。解法是共享 `CameraService`（T-11），一处建设三处受益。
5. **今日建议 Top3 动作**（详见第五节 T-01~T-03）：Modbus TCP ≈ 4-5 人天；方案级基准图+位置修正 ≈ 3-4 人天；IO 输出条件 ≈ 2 人天；**紧随其后的 T-11 采集即用管道（4-5 人天）与 T-02 接口同期设计**——第一梯队合计 ~14 人天后，QDV 在"能上产线"与"上手顺手"两个维度均对齐 SCMVS。

## 三、与参考文件的逐项对标差异

### 3.1 产品形态与模块映射

| SCMVS 模块（视频实证） | QDV 对应 | 差距判定 |
|---|---|---|
| ① 相机设置（设备发现/IP/固件/用户权限） | CameraView（OpenCV VideoCapture 枚举） | **差距**：无厂商 SDK 深度绑定（固件 OTA、序列号、GigE 专属参数）；但换来相机无关性 |
| ② 方案管理（增删改/导入导出/缩略图切换） | SchemeView + SchemeManager（.qdvproj） | **基本对齐**，QDV 多版本字段/Schema 校验 |
| ③ IO 设置（分配/输出条件/IO 监视器） | IOView + IOController（模拟） | **差距**：输出条件表达式、电平/脉宽参数、实时监视器均缺 |
| ④ 通信设置（Modbus 四区 + FTP） | CommView（TCP + 串口存根） | **Critical 差距**：无 Modbus/FTP |
| ⑤ 辅助工具（图像/模型/固件管理） | TrainingInferenceView + ModelManager | **QDV 反超**：训练闭环 + 零样本；缺固件升级 |
| ⑥ 运行监控（OK 率/计数/回放） | MonitorView（passRate 已有） | **部分差距**：缺 4 路状态卡、历史结果行回放图像、工具级耗时分解展示（elapsedMs 数据已有，聚合 UI 缺） |

### 3.2 核心工作流范式差异（本参考文件的最重要新洞察）

SCMVS 采用**四步引导式工作流**：

```
步骤1 相机参数 → 步骤2 基准图 → 步骤3 工具链 → 步骤4 输出
                     │
        基准图 + 位置修正 = 所有算子的参照坐标系，
        预除工件位移，多基准图支持多规格并存
```

QDV 采用**自由节点画布**（QML EditView + 连线拓扑 + 上游链 DFS）：

- QDV 优势：灵活（任意拓扑、分支、循环、单算子调试、整链部署运行）；
- QDV 代价：**新人门槛高**（70 算子 + 自由连线 vs SCMVS 的顺序引导），且**无方案级基准图机制**——PositionCorrectTool 仅是算子级能力，未提升为"步骤 2 基准图注册 → 全部 ROI 相对基准坐标系"的方案属性。工件位置漂移时 SCMVS 全局免疫，QDV 需逐算子手工配位置修正。

### 3.3 深度学习体验差异

| 维度 | SCMVS | QDV |
|---|---|---|
| 异常检测 | "注册图像"极简流：采图→标 OK/NG→自动训练→出 .scbin | AiClassify + 训练视图（流程更重，指标更全：四维校验/健康分） |
| 种类识别 | 模型注入 + 最小置信度/最低得分 50 | DetectObjectsDl + ModelManager manifest |
| 推理位置 | 相机端（ARM-Linux，脱机运行，算法耗时 ~42ms） | PC 端（OpenCV DNN/ORT） |
| 训练能力 | 客户端仅注册式微训 | **完整训练闭环 + 零样本 + 变更台账底座**（反超） |

### 3.4 输出判定差异

- SCMVS：方案结果三选（所有模块 OK / 任意模块 NG / 自定义）+ 单工具最低得分（默认 50）+ 定时输出；
- QDV：BranchControl 算子 + OutputConfigManager + OutputConflictDetector + PortBindingManager（部分对应，且 QDV 的端口绑定/冲突检测比 SCMVS 更精细），但缺"最低得分阈值"这一简单语义与定时输出使能。

### 3.5 交互性专项对标（v2.1 新增：SCMVS 便捷性拆解）

SCMVS 录屏中体现的"顺手"不是单点功能，而是一条**"相机画面贯穿始终、所见即所得"**的交互链。逐项拆解与 QDV 现状（代码核验）如下：

| # | SCMVS 交互（视频实证） | QDV 现状（代码证据） | 差距本质 |
|---|---|---|---|
| I-1 | **采图即基准图**：步骤 2 基准图三来源一键选择（当前图像 / 历史图像 / PC 导入），采一张即设为全局参照 | `EditViewBridge::setCameraFrame`（:1399）**仅记录路径+打日志，管道未实现**；画布图像靠文件加载 | 相机→编辑器的最后一公里断线 |
| I-2 | **采图即训练样本**：异常检测"注册图像"直接采当前相机图 → 标 OK/NG → 一键完成 → 自动训练出模型 | `TrainingInferenceView` 图像来源仅 `QFileDialog`（:552/:562），**无相机采集入口**；训练闭环存在但入口是"翻文件夹" | 训练数据获取比 SCMVS 多 3-4 步操作 |
| I-3 | **编辑全程可见相机画面**：四步向导每一步都基于同一相机实时画面操作（调参立即见效） | CameraView 有实时预览（QTimer+updateFrame:175，v5.3.3 设置对话框实时应用曝光/白平衡:586/:650），但**能力被锁在 CameraView 孤岛**，EditView/TrainingInferenceView 看不到相机 | 组件已有，架构未打通（孤岛问题） |
| I-4 | **底部状态栏实时反馈**：算法耗时 / 工具耗时 / 鼠标坐标 / 像素 RGB（X 7 Y 1179 R 254 G 254 B 254）逐帧刷新 | EditView QML 无像素读数、无坐标显示（grep 仅命中点击容差注释） | 调参时"盲调"，缺量化反馈 |
| I-5 | **一键成像调节**：亮度一键设置/自动调节、机械调焦自动对焦 | CameraView v5.3.3 有**手动**滑块+自动曝光开关（:535），无一键智能调节、无自动对焦 | 从"能调"到"调好"的体验差 |
| I-6 | **方案切换带缩略图一键切**、**结果表行点击回放历史图像** | SchemeView 有列表管理；回放缺（已列 G-5） | 已在 T-05/T-06 覆盖 |

**关键判断**：QDV 并非缺相机能力——CameraView v5.3.3 的实时预览与实时调参、GrabImageTool/OpenFramegrabberTool 的链内采集、setCameraFrame 的预留接口都已存在。真正缺的是一条**共享采集服务 + 三处消费**的架构管道。这正是 SCMVS"方便程度"的骨架，也是 T-11 的设计依据。

## 六、执行建议

1. **今日可立即启动**：T-03（2 人天，纯 Qt 侧无外部依赖）、T-12（0.5-1 人天，QML+C++ 像素查询即可）与 T-02 的 Scheme 字段设计；
2. **T-11 与 T-02 接口同期设计**：CameraService 的帧回调接口与基准图"当前取景"来源本就是同一管道，先定接口（信号 `frameReady(QImage)` + 槽 `capture()`）再分工实现，避免二次返工；T-11 落地后 T-09 的注册模板只差 UI 壳；
3. **T-01 需先做选型决策**：Qt Modbus（QModbusTcpServer/Client，Qt 6.11 自带，零新依赖）vs libmodbus（C 库需 MinGW 编译）——**建议 Qt Modbus**，与现有 Qt Network 体系一致；
4. **验收标准**：T-01 用 Modbus Poll/Modbus Slave 工具对读对写；T-02 用平移 20px 的测试图验证 ROI 自动跟随；T-03 用 IO 采集卡或 PLC 实测脉宽；T-11 验收 = 在编辑器内连续"取景→抓帧→设为基准图→采图注册 NG 样本"全程不离开当前视图（对标 SCMVS 录屏的操作步数）；
5. **风险提示**：G-2 基准图改造触及 Scheme 序列化格式（需版本号 +1 并保留旧版反序列化兼容，参照现有 `version: 2.1.0` 机制）；T-11 共享 VideoCapture 句柄需注意线程归属（采集线程 vs UI 线程的 QImage 跨线程传递，走 queued signal 即可，QDV 已有 P0 卡顿治理的异步日志先例）。
